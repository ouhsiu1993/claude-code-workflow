# Claude Code Workflow

我是產品經理，同時每天使用 Claude Code 開發。這個 repo 收錄我將專案管理上的既有做法，套用到 AI 協作上的設定。繁體中文。

目前收錄一個 output style（輸出風格）：`star-report`。

---

## output style 是什麼

Claude Code 允許以一份 markdown 檔案定義它的回覆方式。

它只影響回報，不影響工程能力。讀取程式碼、使用工具、解決問題的行為完全不變，改變的只有完成之後如何說明。

官方內建數種風格，也可以自行撰寫後放入指定資料夾。這個 repo 收錄的是我自己撰寫的版本。

---

## 為什麼寫這份

有一次 Claude Code 回報「已完成並通過測試」，而該專案裡並沒有測試檔案。單一次不構成問題，累積幾次之後，會變成無法信任任何一句回報。

另外兩種狀況也經常出現。一是指定修改某處，它同時調整了其他看起來不理想的地方，發現時 diff 已經難以逐項確認。二是回覆通篇使用技術術語，自己看得懂，但要轉述給其他人時必須重新翻譯。

這些都可以透過明確定義回報規則來解決。

---

## 三條規則解決的是同一個問題

> **AI 的產出無法直接轉述。**

對產品經理而言，程式碼完成並不是終點。進度要向上匯報、變更要向客戶說明、決策理由要與設計師同步。如果 AI 交付的是一段技術描述，就必須先自行理解、再轉譯一次，同一件事做了兩遍。

因此這三條的共同目標是：**讓改動說明能夠原封不動轉給他人閱讀。**

| 規則 | 對應的既有紀律 |
|---|---|
| STAR 說明 | 借自績效檢討與事件報告的格式，利害關係人本來就在閱讀這類文件 |
| 額外發現另立區塊 | 變更管理：範圍外的事項先提出，不逕行處理 |
| 專有名詞白話解釋 | 利害關係人溝通：產出需能直接轉述，不需二次翻譯 |

工程師較少遇到這個問題，因為他們能直接理解輸出、自行判斷範圍、也不需要對外說明。這三條規則主要服務需要向上或向外交代的角色。

---

## 三條規則

### 一、每次程式碼改動 → 用 STAR 說明

只要動到程式碼，回覆結尾必須包含這段：

```
### 改動說明
遇到什麼問題：（原本的行為哪裡不對、使用者會看到什麼症狀）
目標是什麼：（這次要達成的狀態）
做了什麼：（動了哪些地方、用什麼方式解）
結果是什麼：（現在的行為變成怎樣；有沒有驗證過、怎麼驗的）
```

STAR 是績效檢討與事件報告常用的格式，它的作用是強制從問題敘述開始，而非從執行動作開始。技術回報最常見的問題正是直接跳到「做了什麼」，略過「為什麼要做」。

兩條附加規則比格式本身更重要：

**「遇到什麼問題」須從使用者可見的現象敘述。** 寫「按下送出後畫面沒有反應」，而非「promise 沒有 resolve」。這樣產出的說明才能直接提供給非工程背景的讀者。

**「結果是什麼」不得灌水。** 未執行測試就註明未執行，執行後失敗就附上結果，只有實際驗證過才寫「已確認」。這是三條規則中最關鍵的一條，它直接決定回報的可信度。

### 二、順手發現、但不在這次範圍內的問題 → 另立區塊

發現其他問題時，不逕行修改，也不略過不提：

```
### 另外發現
發現了什麼：（現象）
可能／確定的原因：（明確區分「確定」與「推測」）
打算怎麼做：（建議的下一步；需要決策時直接詢問）
```

這是變更管理的基本原則：**範圍外的事項應先提出，而非逕行處理。** 提出之後由我決定現在處理、後續處理或不處理，決策權保留在我這一側。

寫成獨立區塊之後，執行範圍不會被擴大，發現的問題也不會遺失。

### 三、專有名詞 → 附白話解釋

第一次出現即解釋，說明兩件事：這是什麼、為什麼此處要用它。

> 這裡用了 debounce（把短時間內連續觸發的動作壓成最後一次才執行。
> 使用者打字時每個字都會打一次伺服器，很浪費，所以等他停手 300 毫秒才送出）。

這條的實際用途是降低轉述成本。改動說明若能直接提供給非工程背景的同事閱讀，就省去中間的翻譯環節。

解釋的對象是沒有工程背景的讀者，因此若解釋本身又出現新的專有名詞，即為撰寫失敗，應重寫。

## 安裝

### 1. 選擇檔案

| 作業系統 | 使用檔案 |
|---|---|
| Windows（PowerShell） | `output-styles/star-report-windows.md` |
| macOS / Linux（bash、zsh） | `output-styles/star-report-unix.md` |

兩份內容相同，差異僅在於它建議執行的指令採用哪種 shell 語法。

### 2. 放入指定資料夾

若要讓所有專案套用，放在使用者層級。先建立資料夾：

macOS / Linux：
```bash
mkdir -p ~/.claude/output-styles
```

Windows PowerShell：
```bash
New-Item -ItemType Directory -Force "$HOME\.claude\output-styles"
```

接著將檔案複製進去，副檔名保留 `.md`。

若只要單一專案套用，在專案根目錄建立 `.claude/output-styles/` 後放入即可。專案層級的設定會覆蓋使用者層級。

### 3. 啟用

在 Claude Code 中輸入：

```bash
/output-style
```

會列出可用的 output style，選擇 `star-report`。也可以直接指定：

```bash
/output-style star-report
```

切回預設：

```bash
/output-style default
```

### 4. 確認生效

指定它修改任一檔案，回覆結尾出現「### 改動說明」四段即表示已生效。

## 套用前後對照

**套用前**

> 已修正 `useEffect` 的 dependency array，加入 `userId` 避免 stale closure。
> 同時重構了 `fetchProfile` 改用 `useCallback` memoize，並補上 error boundary。
> 已完成測試。

**套用後**

> 已修正個人資料頁的問題。
>
> ### 改動說明
> **遇到什麼問題**：切換使用者之後，個人資料頁仍顯示上一個使用者的資料。
> **目標是什麼**：切換使用者後，畫面應同步更新為新使用者的資料。
> **做了什麼**：原本的資料抓取只在頁面首次載入時執行，改為使用者變動時一併重新抓取。
> **結果是什麼**：本機切換三個帳號皆正確更新。**單元測試未執行**，此專案目前沒有相關測試。
>
> ### 另外發現
> **發現了什麼**：抓取資料失敗時整頁空白。
> **確定的原因**：此頁面沒有錯誤處理，請求失敗時元件直接拋出例外。
> **打算怎麼做**：建議加上錯誤畫面，但此項超出本次範圍。是否一併處理？

套用前的版本看起來專業，但無法判斷驗證程度，也不確定 error boundary 是否為它自行加入。套用後的版本明確標示了這兩點，且整段可直接用於週報或客戶說明。

## 修改為自己的版本

以下為我的偏好設定，可依需求直接修改檔案。

若不使用 STAR 四段，可替換為團隊既有的格式。若讀者皆為工程背景，第三條白話解釋可以移除，能減少可觀的 token 消耗。檔案中目前將 `api`、`sdk`、`schema` 列為免解釋名詞，此清單可依團隊調整。若要更換語言，修改「全程使用繁體中文」該行即可。

檔案開頭的 frontmatter 決定它在 `/output-style` 選單中的顯示方式：

```yaml
---
name: star-report
description: 每次程式碼改動用 STAR 說明、額外問題另立區塊、專有名詞附白話解釋
---
```

修改 `name` 之後，指令也須一併調整。
