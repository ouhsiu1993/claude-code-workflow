# Claude Code Workflow

我每天用 Claude Code 寫程式，累積下來的工作流設定。繁體中文。

目前收錄一組 **output style（輸出風格）**：`star-report`。

---

## 這在解決什麼問題

用 AI 輔助開發久了，最消耗人的通常不是它寫得好不好，而是**它怎麼回報**。三件事反覆發生：

**一、宣稱做完了，但沒驗證過。**
回覆寫「已完成並通過測試」，實際上一個測試都沒跑。你相信了，上線才爆。

**二、叫它修 A，它順手改了 B。**
過程中看到別的問題就自己動手，範圍悄悄擴大。等你發現時，diff 已經看不完了。

**三、整段回覆是術語牆。**
自己看得懂，但要轉述給非工程背景的同事、主管、客戶時，得再翻譯一次。

這三件都不是模型能力的問題，是**回報規範沒有被定義**。所以我把規範寫下來。

---

## star-report 的三條規則

### 一、每次程式碼改動 → 用 STAR 說明

只要動到程式碼，回覆結尾要有這段：

```
### 改動說明
遇到什麼問題：（原本的行為哪裡不對、使用者會看到什麼症狀）
目標是什麼：（這次要達成的狀態）
做了什麼：（動了哪些地方、用什麼方式解）
結果是什麼：（現在的行為變成怎樣；有沒有驗證過、怎麼驗的）
```

關鍵在兩條附加規則：

- **「遇到什麼問題」要從使用者看得到的現象講起。**
  寫「按下送出後畫面卡住沒反應」，不要只寫「promise 沒 resolve」。
- **「結果是什麼」不准灌水。**
  沒跑過測試就說沒跑；跑了失敗就貼結果。只有真的驗證過才寫「已確認」。

### 二、順手發現、但不在這次範圍內的問題 → 另立區塊

看到其他問題時，不要默默修掉，也不要默默略過：

```
### 另外發現
發現了什麼：（現象）
可能／確定的原因：（講清楚是「確定」還是「猜測」）
打算怎麼做：（建議的下一步；需要你拍板就直接問）
```

這條同時解決兩個相反的失敗：**擅自擴大範圍**，和**發現了卻不講**。

### 三、專有名詞 → 附白話解釋

第一次出現就解釋，講兩件事：這是什麼、為什麼這裡要用它。

> 這裡用了 debounce（把短時間內連續觸發的動作壓成最後一次才執行。
> 使用者打字時每個字都會打一次伺服器，很浪費，所以等他停手 300 毫秒才送出）。

解釋是寫給非工程背景的人看的。**如果解釋本身又冒出新的專有名詞，代表寫壞了，重寫。**

## 安裝

### 1. 選擇檔案

| 你的系統 | 用這個檔案 |
|---|---|
| Windows（PowerShell） | `output-styles/star-report-windows.md` |
| macOS / Linux（bash、zsh） | `output-styles/star-report-unix.md` |

兩份內容相同，差別只在**它建議你執行的指令用哪種 shell 語法**。

### 2. 放到對的資料夾

**所有專案都套用（放使用者層級）**

macOS / Linux：
```bash
mkdir -p ~/.claude/output-styles
```

Windows PowerShell：
```bash
New-Item -ItemType Directory -Force "$HOME\.claude\output-styles"
```

然後把檔案複製進去，檔名保留 `.md`。

**只有單一專案套用（放專案層級）**

在專案根目錄建立 `.claude/output-styles/`，把檔案放進去。專案層級會蓋過使用者層級。

### 3. 啟用

在 Claude Code 裡輸入：

```bash
/output-style
```

會列出所有可用的 output style，選 `star-report` 即可。也可以直接指定：

```bash
/output-style star-report
```

切回預設：

```bash
/output-style default
```

### 4. 確認生效

隨便叫它改一個檔案。如果回覆結尾出現「### 改動說明」四段，就是生效了。

## 前後對照

**套用前**

> 已修正 `useEffect` 的 dependency array，加入 `userId` 避免 stale closure。
> 同時重構了 `fetchProfile` 改用 `useCallback` memoize，並補上 error boundary。
> 已完成測試。

**套用後**

> 已修正個人資料頁的問題。
>
> ### 改動說明
> **遇到什麼問題**：切換使用者之後，個人資料頁還是顯示上一個使用者的資料。
> **目標是什麼**：切換使用者後，畫面要跟著換成新使用者的資料。
> **做了什麼**：原本的資料抓取只在頁面第一次載入時執行，改成「使用者變動時也重抓」。
> **結果是什麼**：本機切換三個帳號都正確更新。**單元測試沒有跑**，這個專案目前沒有相關測試。
>
> ### 另外發現
> **發現了什麼**：抓資料失敗時整頁會白屏。
> **確定的原因**：這個頁面沒有錯誤處理，請求失敗時元件直接拋錯。
> **打算怎麼做**：建議加上錯誤畫面，但這超出這次的範圍。要我一起處理嗎？

差別不在字多字少，在於：**你知道它驗證到什麼程度、知道它發現了什麼卻沒動、而且這段可以直接轉貼給非工程的同事看。**

## 改成你自己的

這份不是標準答案，是我的偏好。直接改檔案就好，幾個常見的調整方向：

- **不用 STAR 四段** — 換成你團隊習慣的格式（例如 Problem / Solution / Risk）
- **不需要白話解釋** — 如果你的讀者全是工程師，刪掉第三條可以省不少 token
- **調整免解釋的名詞清單** — 檔案裡目前把 `api`、`sdk`、`schema` 列為不用解釋，依你的團隊增減
- **改語言** — 把「全程使用繁體中文」改掉即可

檔案開頭的 frontmatter 決定它在 `/output-style` 選單裡怎麼顯示：

```yaml
---
name: star-report
description: 每次程式碼改動用 STAR 說明、額外問題另立區塊、專有名詞附白話解釋
---
```

`name` 改了，指令也要跟著改（`/output-style 你的新名字`）。
