# Claude Code Workflow

[English](README.en.md)

AI 把程式寫完之後，真正花時間的是把它講給別人聽。

這個 repo 收錄一份 Claude Code 的 output style，內容是把專案管理既有的回報紀律，搬到人與 AI 之間。繁體中文。

---

## output style 是什麼

Claude Code 允許用一份 markdown 檔案，定義它回覆的方式。

它只管回報，不碰工程。讀程式碼、用工具、解問題的行為完全不變，改變的只有做完之後怎麼交代。

官方內建數種，也可以自己寫一份放進指定資料夾。這裡收錄的是我自己寫的版本。

---

## 起因

模型一直在變強，推理的時間也越拉越長。等得久，期待自然跟著往上。

但這幾個版本用下來，回報的品質沒有跟上推理的品質。整段專業術語、講不到重點、或者跑完之後沒有結論——你得再問一次「所以修好了嗎」、「這句話是什麼意思」。

代價是雙重的。追問一次，token 再燒一輪，而現在每一輪的等待時間都比從前長。趕著修 bug、趕著上線、趕著出報告的時候，這個成本直接反映在時程上。

久了還會變成另一件事：不敢相信它的回報。它說「已完成並通過測試」，那個專案裡沒有測試檔案。單一次不構成問題，累積幾次之後，連它真的做對的時候，你也不會直接採信。

另外兩種狀況也反覆出現。指定修改某處，它順帶調整了其他看起來不理想的地方，等發現時 diff 已經難以逐項確認。或者回覆通篇術語，自己讀得懂，要轉給別人時得重寫一遍。

這些都與程式碼品質無關。它們發生在交付之後。

---

## 三條規則，同一個問題

程式碼完成不是終點，是交代的開始。

進度要向上匯報、變更要向客戶說明、決策理由要跟設計師同步。如果 AI 交出來的是一段技術描述，我得先自己讀懂、再翻譯一次。同一件事做兩遍。

所以這三條規則的目標只有一個：**讓改動說明可以原封不動轉出去。**

| 規則 | 對應的既有紀律 |
|---|---|
| STAR 說明 | 借自績效檢討與事件報告的格式，利害關係人本來就在讀這種文件 |
| 額外發現另立區塊 | 變更管理：範圍外的事先提出，不逕行處理 |
| 專有名詞白話解釋 | 利害關係人溝通：產出要能直接轉述，不需二次翻譯 |

這三條對工程師幫助有限。他讀得懂輸出、自己決定範圍、不必對誰交代。真正需要的，是每天都在轉述的人。

---

## 三條規則

### 一、每次程式碼改動 → 用 STAR 說明

只要動到程式碼，回覆結尾必須包含這段：

```
### 改動說明
遇到什麼問題：（原本的行為哪裡不對、使用者會看到什麼症狀）
目標是什麼：（這次要達成的狀態）
做了什麼：（動了哪些地方、用什麼方式解）
結果是什麼：（現在的行為變成怎樣；有沒有驗證過、怎麼驗的）
```

STAR 是績效檢討與事件報告的既有格式。它的作用是強迫從問題開始敘述，而不是從動作開始——技術回報最常見的毛病，正是跳過「為什麼要做」直接講「做了什麼」。

兩條附加規則比格式本身重要：

**「遇到什麼問題」從使用者看得見的現象寫起。** 寫「按下送出後畫面沒有反應」，不要寫「promise 沒有 resolve」。這樣產出的說明才能直接交出去。

**「結果是什麼」不得灌水。** 沒跑測試就寫沒跑，跑了失敗就附上結果，只有真的驗證過才寫「已確認」。三條裡最關鍵的一條——回報能不能信，看的就是這裡。

### 二、順手發現、但不在這次範圍內的問題 → 另立區塊

發現其他問題時，不逕行修改，也不略過不提：

```
### 另外發現
發現了什麼：（現象）
可能／確定的原因：（明確區分「確定」與「推測」）
打算怎麼做：（建議的下一步；需要決策時直接詢問）
```

這是變更管理的基本原則：**範圍外的事先提出，不逕行處理。** 提了之後由我決定現在做、之後做、還是不做。決策權留在我這邊。

寫成獨立區塊，執行範圍不會被悄悄擴大，發現的東西也不會消失。

### 三、專有名詞 → 附白話解釋

第一次出現即解釋，說明兩件事：這是什麼、為什麼此處要用它。

> 這裡用了 debounce（把短時間內連續觸發的動作壓成最後一次才執行。
> 使用者打字時每個字都會打一次伺服器，很浪費，所以等他停手 300 毫秒才送出）。

這條在省轉述成本。改動說明若能直接交給非工程背景的同事，中間那層翻譯就不必存在。

解釋的對象是沒有工程背景的人。如果解釋本身又長出新的專有名詞，就是寫壞了，重寫。

## 安裝

### 1. 選擇檔案

| 作業系統 | 使用檔案 |
|---|---|
| Windows（PowerShell） | `output-styles/zh-TW/star-report-windows.md` |
| macOS / Linux（bash、zsh） | `output-styles/zh-TW/star-report-unix.md` |

兩份內容相同，差異只在它建議執行的指令採用哪種 shell 語法。

### 2. 放入指定資料夾

要讓所有專案套用，放在使用者層級。先建立資料夾：

macOS / Linux：
```bash
mkdir -p ~/.claude/output-styles
```

Windows PowerShell：
```bash
New-Item -ItemType Directory -Force "$HOME\.claude\output-styles"
```

再把檔案複製進去，副檔名保留 `.md`。

只要單一專案套用的話，在專案根目錄建立 `.claude/output-styles/` 後放入即可。專案層級會覆蓋使用者層級。

### 3. 啟用

在 Claude Code 中輸入：

```bash
/output-style
```

會列出可用的 output style，選擇 `star-report`。也可以直接指定：

```bash
/output-style star-report
```

切回預設：

```bash
/output-style default
```

### 4. 確認生效

指定它修改任一檔案，回覆結尾出現「### 改動說明」四段即為生效。

## 套用前後

**套用前**

> 已修正 `useEffect` 的 dependency array，加入 `userId` 避免 stale closure。
> 同時重構了 `fetchProfile` 改用 `useCallback` memoize，並補上 error boundary。
> 已完成測試。

**套用後**

> 已修正個人資料頁的問題。
>
> ### 改動說明
> **遇到什麼問題**：切換使用者之後，個人資料頁仍顯示上一個使用者的資料。
> **目標是什麼**：切換使用者後，畫面應同步更新為新使用者的資料。
> **做了什麼**：原本的資料抓取只在頁面首次載入時執行，改為使用者變動時一併重新抓取。
> **結果是什麼**：本機切換三個帳號皆正確更新。**單元測試未執行**，此專案目前沒有相關測試。
>
> ### 另外發現
> **發現了什麼**：抓取資料失敗時整頁空白。
> **確定的原因**：此頁面沒有錯誤處理，請求失敗時元件直接拋出例外。
> **打算怎麼做**：建議加上錯誤畫面，但此項超出本次範圍。是否一併處理？

前者看起來專業，卻無法判斷它驗證到什麼程度，也不知道 error boundary 是不是它自己加的。後者把這兩件事都寫明了，而且整段可以直接貼進週報。
