# Claude Code Workflow

我是產品經理，同時每天用 Claude Code 寫程式。這裡放的是我把專案管理上習慣的做法，搬到跟 AI 協作上的設定。繁體中文。

目前只有一個 output style（輸出風格）：`star-report`。

---

## 先說 output style 是什麼

Claude Code 允許你用一份 markdown 檔，改變它「回覆你的方式」。

重點是它**只改回報，不改工程能力**——它怎麼讀程式碼、怎麼用工具、怎麼解問題全部照舊，只有「做完之後怎麼跟你交代」會照你寫的規則走。所以套用之後不會變笨，這點可以放心。

官方內建幾種風格，也可以自己寫一份放進資料夾。這個 repo 就是我自己寫的那份。

---

## 為什麼寫這個

有次 Claude Code 回報「已完成並通過測試」，我信了，後來才發現那個專案裡連測試檔都沒有。單一次不嚴重，累積幾次之後，你會開始不敢相信任何一句回報。

另外兩個也常遇到。一個是叫它修某個地方，它順手把旁邊看不順眼的也改了，等我發現時 diff 已經看不完。另一個是回覆整段都是術語，自己勉強看得懂，但要轉述給別人時得再翻譯一遍。

這些靠把回報規則寫清楚就能解決，所以就寫了一份。

---

## 這三條規則其實是同一件事

一開始我是分開處理的，寫完才發現它們在解決同一個問題：

> **AI 產出的東西，我沒辦法直接轉述出去。**

程式碼寫完對 PM 來說不是結束。我要跟老闆講進度、跟客戶講改了什麼、跟設計師講為什麼這樣做。如果 AI 給我的是一段技術描述，我得先自己讀懂、再翻譯一次——等於同一件事做兩遍。

所以這三條的共同目標是：**讓改動說明可以原封不動貼給別人看。**

| 規則 | 對應的既有紀律 |
|---|---|
| STAR 說明 | 借自績效檢討與事件報告的格式，利害關係人本來就在讀這種東西 |
| 額外發現另立區塊 | 變更管理：範圍外的事要先報備，不是自己做掉 |
| 專有名詞白話解釋 | 利害關係人溝通：產出要能直接轉述，不需要二次翻譯 |

純工程師其實不太需要這三條——他自己看得懂、自己決定範圍、也不用跟誰交代。**會痛的是需要對上、對外交代的人。**

---

## 三條規則

### 一、每次程式碼改動 → 用 STAR 說明

只要動到程式碼，回覆結尾要有這段：

```
### 改動說明
遇到什麼問題：（原本的行為哪裡不對、使用者會看到什麼症狀）
目標是什麼：（這次要達成的狀態）
做了什麼：（動了哪些地方、用什麼方式解）
結果是什麼：（現在的行為變成怎樣；有沒有驗證過、怎麼驗的）
```

STAR 是寫績效檢討跟事件報告時常用的格式，好處是它強迫「從問題講起」而不是「從動作講起」。技術回報最常見的毛病就是直接跳到做了什麼，跳過為什麼要做。

有兩條附加規則，實際上比格式本身重要：

**「遇到什麼問題」要從使用者看得到的現象講起。** 寫「按下送出後畫面卡住沒反應」，不要只寫「promise 沒 resolve」。這樣寫出來的東西才能直接貼給非工程的人看。

**「結果是什麼」不准灌水。** 沒跑過測試就說沒跑，跑了失敗就貼結果，只有真的驗證過才寫「已確認」。這條是我最在意的，因為它直接決定我敢不敢相信回報。

### 二、順手發現、但不在這次範圍內的問題 → 另立區塊

看到其他問題時，不要默默修掉，也不要默默略過：

```
### 另外發現
發現了什麼：（現象）
可能／確定的原因：（講清楚是「確定」還是「猜測」）
打算怎麼做：（建議的下一步；需要你拍板就直接問）
```

這就是變更管理的老規矩：**範圍外的事情要先講，不是自己做掉。** 講了之後我可以決定現在處理、之後處理、還是不處理——決定權在我手上。

寫成獨立區塊之後，範圍不會被偷偷擴大，但發現的東西也不會消失。

### 三、專有名詞 → 附白話解釋

第一次出現就解釋，講兩件事：這是什麼、為什麼這裡要用它。

> 這裡用了 debounce（把短時間內連續觸發的動作壓成最後一次才執行。
> 使用者打字時每個字都會打一次伺服器，很浪費，所以等他停手 300 毫秒才送出）。

這條純粹是為了自己方便。改動說明如果能直接轉給非工程的同事看，中間那層翻譯就省下來了。

解釋是寫給沒有工程背景的人看的，所以如果解釋本身又冒出新的專有名詞，就是寫壞了，重寫。

## 安裝

### 1. 選檔案

| 你的系統 | 用這個 |
|---|---|
| Windows（PowerShell） | `output-styles/star-report-windows.md` |
| macOS / Linux（bash、zsh） | `output-styles/star-report-unix.md` |

兩份內容一樣，差別只在它建議你執行的指令用哪種 shell 語法。

### 2. 放到對的資料夾

想讓所有專案都套用，放使用者層級。先建資料夾：

macOS / Linux：
```bash
mkdir -p ~/.claude/output-styles
```

Windows PowerShell：
```bash
New-Item -ItemType Directory -Force "$HOME\.claude\output-styles"
```

然後把檔案複製進去，檔名保留 `.md`。

只想讓單一專案套用的話，在專案根目錄建 `.claude/output-styles/` 放進去就好，專案層級會蓋過使用者層級。

### 3. 啟用

在 Claude Code 裡輸入：

```bash
/output-style
```

會列出可用的 output style，選 `star-report`。也可以直接指定：

```bash
/output-style star-report
```

要切回預設：

```bash
/output-style default
```

### 4. 確認生效

隨便叫它改一個檔案，回覆結尾出現「### 改動說明」四段就是生效了。

## 套用前後長這樣

**前**

> 已修正 `useEffect` 的 dependency array，加入 `userId` 避免 stale closure。
> 同時重構了 `fetchProfile` 改用 `useCallback` memoize，並補上 error boundary。
> 已完成測試。

**後**

> 已修正個人資料頁的問題。
>
> ### 改動說明
> **遇到什麼問題**：切換使用者之後，個人資料頁還是顯示上一個使用者的資料。
> **目標是什麼**：切換使用者後，畫面要跟著換成新使用者的資料。
> **做了什麼**：原本的資料抓取只在頁面第一次載入時執行，改成使用者變動時也重抓。
> **結果是什麼**：本機切換三個帳號都正確更新。**單元測試沒有跑**，這個專案目前沒有相關測試。
>
> ### 另外發現
> **發現了什麼**：抓資料失敗時整頁會白屏。
> **確定的原因**：這個頁面沒有錯誤處理，請求失敗時元件直接拋錯。
> **打算怎麼做**：建議加上錯誤畫面，但這超出這次的範圍。要我一起處理嗎？

前面那版看起來很專業，但你不知道它到底驗證到什麼程度，也不知道 error boundary 是不是它自己順手加的。後面那版把這兩件事都講清楚了——而且整段可以直接貼進週報或客戶信裡，不用再改寫。

## 改成你自己的

這是我的偏好，不見得適合你，直接改檔案就好。幾個常見的調整：

不用 STAR 四段的話，換成你團隊習慣的格式。讀者全是工程師的話，第三條白話解釋可以刪掉，能省不少 token。檔案裡目前把 `api`、`sdk`、`schema` 列為不用解釋的名詞，這份清單依你的團隊增減。要換語言的話，把「全程使用繁體中文」那行改掉。

檔案開頭的 frontmatter 決定它在 `/output-style` 選單裡怎麼顯示：

```yaml
---
name: star-report
description: 每次程式碼改動用 STAR 說明、額外問題另立區塊、專有名詞附白話解釋
---
```

`name` 改了，指令也要跟著改。
